# review-pr — 목적을 먼저 잡고, 결함은 끝까지 추적해서 보고한다

이 스킬의 리뷰는 "diff를 훑어 의심스러운 줄을 나열하는 것"이 아니다. 리뷰어가 실제로 하는 일, 즉 **이 PR이 무엇을 하려는지 이해하고, 그대로 됐는지 보고, 문제가 있다면 그것이 정말 유저에게 닿는 문제인지 확인한 뒤, 작성자가 바로 움직일 수 있게 보고하는 것**을 그대로 따른다.

순서가 중요하다. 목적을 모르고 코드를 보면 "의도된 동작"을 결함으로 지적하게 되고, 결함을 호출부까지 추적하지 않으면 도달 불가능한 코드를 두고 호들갑을 떨게 된다. 둘 다 작성자의 시간을 뺏고 리뷰어의 신뢰를 깎는다.

## 입력

- PR 번호 또는 URL. 저장소가 불분명하면 현재 디렉터리의 `origin`을 쓴다.
- 아무것도 없으면 현재 브랜치에 열린 PR을 찾는다 (`gh pr view` 가 반환하면 그 PR).
- PR 없이 "지금 브랜치 변경 봐줘"라면 base 브랜치 대비 diff만으로 진행한다. 이때 1)의 목적은 커밋 메시지와 diff에서 추론하고, 그렇게 했다고 보고서에 적는다.

## 절차

### 0) 준비

1. `command -v gh` 로 gh CLI를 확인한다. 없으면 `brew install gh && gh auth login` 을 안내하고 멈춘다.
2. 저장소에 코드 규칙이 있으면 먼저 읽는다. 프로젝트 전용 코드 작성 가이드 스킬(예: `local-code-writing-guide`), `CLAUDE.md`, `AGENTS.md`, 린트 설정 순으로 찾는다. 이 규칙은 3)에서 P2 판단의 기준이 된다. 없으면 일반적인 기준만 쓴다.
3. 코드를 탐색할 수 있게 PR 브랜치를 확보한다. 4)에서 호출부를 따라가려면 diff만으로는 부족하다.
   - 현재 체크아웃된 브랜치가 PR의 `headRefName` 이면 그대로 쓴다.
   - 아니면 사용자의 작업 트리를 건드리지 않도록 **별도 워크트리**를 만든다. 포크 PR도 같은 명령으로 된다.
     ```bash
     git fetch origin pull/<번호>/head
     git worktree add <스크래치 디렉터리>/<레포명>-pr-<번호> FETCH_HEAD
     ```
     리뷰가 끝나면 `git worktree remove` 로 지운다.
   - 저장소가 로컬에 없으면 diff만으로 진행하고, 보고서에 "호출부 미확인"을 명시한다.

### 1) 목적 파악 — 이 PR은 무엇을 이루려 하는가

`${CLAUDE_SKILL_DIR}/scripts/fetch-pr-context.sh <owner/repo> <번호>` 를 실행한다. 본문, 이슈 코멘트, 리뷰, 인라인 리뷰 코멘트, 변경 파일 목록을 한 번에 JSON으로 준다. (권한 자동 승인을 받으려면 이 경로 그대로, `bash` 프리픽스나 파이프 없이 실행한다.)

읽고 나서 다음을 정리한다.

- **목적**: 유저 또는 시스템에 무엇이 달라지는가. 한 문장.
- **범위**: 본문이 말하는 변경 범위. 변경 파일 목록과 대조해 본문에 없는 파일이 있으면 적어 둔다.
- **이미 합의된 것**: 코멘트 스레드에서 리뷰어와 작성자가 이미 결론 낸 것. 같은 지적을 반복하면 안 되므로 반드시 확인한다. 해결(resolved)된 스레드의 지적이 코드에 반영됐는지는 2)에서 본다. 단, 스레드에서 다루지 않은 **새 결과**(예: 그 결정이 기존 데이터에 미치는 영향)는 합의된 것이 아니므로 올릴 수 있다.
- **작성자가 밝힌 전제**: "이 케이스는 다음 PR에서", "백엔드가 보장함" 같은 말. 전제 자체가 틀렸을 수 있으므로 믿지 말고 기록만 한다.
- **머지 조건**: base 브랜치가 규칙에 맞는지(릴리즈·QA 브랜치나 다른 PR의 head를 가리키는 스택 PR인지), draft 여부, CI 상태. 코드 품질과 별개로 머지 순서나 base 변경이 필요하면 "사람 확인 필요"에 적는다. 이걸 빼먹으면 코드는 좋은데 엉뚱한 브랜치에 머지되는 사고를 리뷰가 못 막는다.

본문이 비어 있거나 티켓 번호뿐이면 diff와 커밋 메시지로 목적을 추론하고, 추론했다고 표시한다.

### 2) 목적 대비 구현 확인

목적을 기준으로 diff를 읽는다. 결함을 찾는 게 아니라 **"하겠다고 한 것을 했는가"**만 본다.

- **누락**: 목적에 필요한데 빠진 것 (예: "모든 목록 화면에 적용"인데 한 화면이 빠짐)
- **초과**: 목적과 무관한 변경 (리팩터링, 포맷팅, 다른 기능). 리뷰어가 놓치기 쉬운 범위 확대가 섞여 있으면 그 자체가 지적 대상이다.
- **상이**: 본문의 설명과 코드가 하는 일이 다름

코멘트에서 요청됐고 작성자가 "반영했다"고 한 항목은 실제 반영됐는지 코드로 확인한다.

### 3) 결함 탐지

`+` 로 추가·변경된 줄을 중심으로 본다. 기존 코드의 문제는 이 PR의 책임이 아니므로 **참고**로만 분리한다. 단, 이 PR이 그 기존 코드를 새로 호출하기 시작했다면 PR의 문제다.

심각도 기준:

| 등급 | 기준 |
|---|---|
| 🔴 P0 | 크래시, 데이터 손실·오염, 보안 취약점, 메모리 누수 |
| 🟡 P1 | 잠재적 버그, 엣지 케이스 미처리, 성능 저하, 2)에서 찾은 범위 확대·설명과 다른 동작 |
| 🟠 P2 | 0)에서 읽은 프로젝트 규칙 위반, 구조 문제, 설명 누락 |
| 🟢 P3 | 가독성, 네이밍, 스타일 |

이 단계의 결과는 **후보**다. 아직 보고하지 않는다. 다음 두 단계에서 걸러진다.

### 4) 실제 이슈로 이어지는가 — 호출부와 주변 코드 추적

후보마다 다음을 코드에서 확인한다. Grep과 LSP(정의·참조 찾기)를 쓰고, 파일을 열어 읽는다.

- **호출부**: 이 코드를 누가 부르는가. 문제가 되는 입력(null, 빈 목록, 동시 호출, 특정 상태)이 실제로 들어올 수 있는가.
- **가드**: 상위에서 이미 막고 있는가 (타입, 선행 검증, 플래그, try/catch).
- **데이터 흐름**: 문제의 값이 어디서 오고 어디로 가는가. 중간에 변환·필터가 있는가.
- **생명주기·동시성**: 비동기, 화면 전환, 재생성 시점에 어떤 순서로 실행되는가.

결과는 셋 중 하나다.

- **확정**: 문제 입력이 들어오는 경로를 찾았다. 그 경로의 `파일:줄`이 근거가 된다.
- **기각**: 가드가 있거나 그 입력이 올 수 없다. 보고서의 "확인했으나 이슈 아님"에 한 줄로 남긴다. 기각한 것을 적는 이유는, 작성자나 다른 리뷰어가 같은 의심을 할 때 재검토를 아끼기 위해서다.
- **판단 불가**: 코드만으로 모르는 것(서버 응답 보장, 운영 설정). "사람 확인 필요"로 보낸다. 모르는 것을 확정처럼 쓰지 않는다.

### 5) 유저가 재현할 수 있는가

확정된 이슈마다 **유저 관점의 재현 경로**를 쓴다. "A 화면에서 B를 누르고 네트워크가 끊기면"처럼 유저가 밟을 수 있는 순서와 조건이다.

- 재현 경로가 있으면 그것이 **현상** 서술의 재료가 된다.
- 유저가 도달할 수 없는 경로(내부 도구, 디버그 플래그, 데드 코드)면 심각도를 한 단계 내리고 그 이유를 적는다.
- 테스트 코드나 빌드 스크립트의 문제처럼 유저와 무관한 것은 재현 항목에 "유저 영향 없음 — 개발 환경"이라고 쓴다.

### 6) 보고

터미널에서 읽히는 보고서다. 결론을 맨 위에 두고, 이슈는 심각도 순으로, 각 이슈는 아래 다섯 항목을 **빠짐없이** 채운다. 작성자가 이 다섯 가지를 보면 되묻지 않고 바로 고칠 수 있어야 한다.

````markdown
## PR #{번호} 리뷰 — {제목을 다듬은 한 줄}

**목적** {1)에서 정리한 한 문장}
**목적 대비 구현** {일치 / 부분 일치 / 불일치} — {누락·초과·상이 요약, 없으면 생략}
**결론** {머지 가능 / 수정 후 머지 / 재검토 필요} · 이슈 {N}건 (P0 {a} · P1 {b} · P2 {c} · P3 {d})

### 1. [🟡 P1] {무엇이 어떻게 잘못되는지 한 줄}
- **현상**: {유저 또는 시스템에 나타나는 결과}
- **재현**: {유저가 밟는 경로와 조건} / 또는 "직접 재현 경로 없음 — {이유}"
- **원인**: {코드의 어느 부분이 왜} `path/File.kt:42`
- **근거**: {4)에서 확인한 호출부·데이터 흐름} `path/Caller.kt:88`
  ```kotlin
  // 문제 부분 발췌 (필요할 때만, 짧게)
  ```
- **해결 방안**: {추천안}. {대안이 있으면 한 줄로}

### 참고 (기존 코드)
- {이 PR 책임은 아니지만 눈에 띈 것} `path:line`

### 확인했으나 이슈 아님
- {의심한 것} — {기각 근거} `path:line`

### 사람 확인 필요
- {코드만으로 판단 못 한 것과, 누가 답할 수 있는지}

GitHub에는 아무것도 남기지 않았습니다. 코멘트로 올리려면 말씀해 주세요.
````

지키는 것:

- **결론**은 이슈의 최고 심각도로 정한다. P0·P1이 하나라도 확정이면 "수정 후 머지" 이상.
- 이슈가 없으면 이슈 절을 생략하고 결론에 "이슈 없음"이라고 쓴다. 억지로 P3를 채우지 않는다. 대신 결론 바로 아래에 **"수정이 동작하는 근거"** 절을 두고, 4)에서 확인한 사실을 `파일:줄`과 함께 3~5줄로 적는다. "이슈 없음"만 있으면 작성자도 리뷰어도 무엇을 확인했는지 알 수 없다.
- **참고**, **확인했으나 이슈 아님**, **사람 확인 필요**는 내용이 없으면 절을 통째로 뺀다. 각 절은 3줄을 넘기지 않는다.
- 코드 발췌는 원인을 보여 주는 데 필요한 줄만. diff 전체를 다시 싣지 않는다.
- 2)에서 추론으로 채운 목적이나 0)에서 호출부를 못 본 경우는 **목적** 또는 **결론** 줄 끝에 괄호로 밝힌다. 예: `(목적은 diff에서 추론)`, `(로컬 저장소 없음 — 호출부 미확인)`.

### 7) GitHub에 쓰지 않는다

사용자가 **명시적으로** "코멘트 남겨줘", "리뷰 올려줘"라고 하기 전에는 `gh pr comment`, `gh pr review`, `gh api` 의 쓰기 호출을 하지 않는다. 리뷰 코멘트는 사용자 이름으로 동료에게 가는 말이고, 올린 뒤에는 되돌릴 수 없다. "리뷰해줘"는 보고서를 달라는 뜻이지 게시하라는 뜻이 아니다.

명시적 요청이 왔을 때는, 올릴 코멘트 전문과 대상(PR 전체 / 어느 파일 어느 줄)을 먼저 보여 주고 확인을 받은 뒤 올린다. 코멘트 문장을 다듬고 싶으면 `softkit:communicator` 에이전트(채널=PR 코멘트)를 쓸 수 있고, 없으면 보고서의 현상·원인·해결 방안을 그대로 간결하게 옮긴다.

## 스크립트

| 스크립트 | 용도 |
|---|---|
| `scripts/fetch-pr-context.sh <owner/repo> <번호>` | PR 본문·코멘트·리뷰·인라인 코멘트·변경 파일을 JSON 하나로. 조회 전용 |

diff는 `gh pr diff <번호> --repo <owner/repo>` 로 받는다. 파일이 많으면 `--name-only` 로 목록을 먼저 보고 파일 단위로 나눠 읽는다.
